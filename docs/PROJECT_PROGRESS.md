## Container image vulnerability scanning and triage policy — 2026-11-07

- CI now runs a pinned Trivy v0.76.2 scan against the backend image for OS and application-library vulnerabilities at HIGH and CRITICAL severity.
- The first scan is inventory-only and always prints all matching findings, including those without an upstream fix. It does not fail the job, so unfixed findings remain visible in the CI log for triage rather than being silently suppressed.
- A second scan uses `ignore-unfixed: true` and fails CI on HIGH/CRITICAL findings for which Trivy reports an available fix. The action remains pinned to immutable commit `ed142fd0673e97e23eac54620cfb913e5ce36c25`; Trivy remains pinned to v0.76.2.
- Exact-HEAD CI `42367103349` failed at the original strict scan. Its report identified 49 HIGH and 0 CRITICAL OS-package findings in Debian 13.7; the listed findings had no fixed-version value in the report. Frontend tests/build, backend tests, dependency audits, and Docker image build all passed on that run. CodeQL run `42367103353` succeeded.
- The policy change does not claim the image is vulnerability-free. It distinguishes actionable findings with an available fix (CI-blocking) from findings with no fix currently reported (visible, non-blocking, and requiring ongoing triage). If an unfixed finding is assessed as unacceptable for deployment, deployment must remain blocked by release review even if CI passes.
- This policy does not replace base-image updates, runtime scanning, or periodic review of newly available fixes. No project progress percentage is increased by changing the scan policy; the new exact-HEAD CI run must verify it.
